# 22 Nov 2026: the table UI from the table pull requests

Kenil asked for the table work in the open pull requests from #94 to be brought onto main by
review and rewrite, never by merging them; his calls are in the core review doc
(https://claude.ai/artifact/PjPbD3f4oXebqxUsg83b9s), Fix as proposed on every row, nine batches.
The first two are window code, ported as built. Batch 2 went first, because the grid PRs were made
on top of its lists row: one frame, lists as pills each with a right-click menu, an icon toolbar,
Properties in ⋮, New · Save ▾ · Cancel and page numbers at the foot, one button shape, no
Timeline and no words where nothing is. The core now reads a list saved as a timeline as a table,
and Alpha's shape tool no longer offers one (views test). Batch 1 on top: the row count once (the
totals row's first cell, or the foot for a view with no totals row), Summarize in an empty totals
cell, + at the right edge, the sideways bar at the frame's foot, choice colours and one dropdown
with search past six and ★, no words over a view's rows, the totals row resting on the foot. Where
a later PR in a chain had already redone what an earlier one changed (the button shapes, the
count beside the chips), the later one stands; ui-rules T1, T3, T5, T25, T26 and L4 merged by hand.

Batch 3, tables open fast, as built, with one list of the marks a cell draws (`CELL_MARKS`) and a
shape-only read for a new column; an empty chips line over a table a connection fills went too.
Batch 4, lists and views per person and Calendar as a view: each person orders a table's lists
(the first is where it opens) and keeps their own view of it (a list only picks rows). The PRs
kept both as one blob per person, rewritten whole; now each is one preference per table and person
(`world/table-prefs.ts`), so two windows never overwrite each other's other tables, and each goes
with its table, its list or its field. A list Alpha lays out for someone sets their view of the
table, and the table's read carries that view so an open window takes it (his first try showed the
window keeping its own), so it opens as made, and the shape tool's words say a list picks rows. A kit says how a
table first opens (`view:`, migration 7, tried on a backup of the Mac's world), its kind and its
lists' kinds checked against one list in the kit format; Calendar 0.2.0 opens Events as a
calendar. A kit update drops a list the kit made and no longer names while nobody changed it, and
from everyone's order (design.md, on his yes). Kept files break ties by when each was kept, which
made one api test flaky.

Batch 5, a choice's default (★): new rows given no value take it, marked as computed from it. It is
now the table's shape like choices and colours: it goes through the shape wall (refused in a
managed module and on a field a connection fills, asked of a kit's maintainer), is written to
module.yaml, and is part of the kit format (`default:` on a choice, checked to be one of its
choices; docs/kit-api.md regenerated). A kit installs its defaults and a newer version brings
its own, unless someone starred another since. Alpha's shape tool sets one (`set_default`).
Changing the choices so the starred one goes says so in the same line. Reading a table's fields
moved out of shape.ts into fields-read.ts, which kept shape.ts under its wall.

Batch 6, Import and Export in ⋮: a CSV or sheet the person drops in goes into a table header by
header, each value keeping its cell as its source; Export is the window's. One import in the world
for the window and Alpha's file tool alike, with the walls of adding rows: refused on a table a
connection fills (D8), allowed in a managed module as rows by hand are. The headers are a read of
their own (GET), the POST only imports, and a file imported into the table before says how many of
its rows are there already: it goes in again only on the person's choice (`again`, in the window
and the tool). Both are doors that add rows (doors.ts), so every rule about adding rows is tried
through them.
