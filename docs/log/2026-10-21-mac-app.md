# 21 October 2026: the Mac app and the companion

Built on Kenil's yes to "Plan: the companion and the Mac app", with his answers: a cute simple
face for the companion for now (not an A; the real shape later), the companion at login, the
Alpha Code Signing certificate later.

- **The shell** (`mac/`, Tauri 2.11.6; its inner crates held at the versions it was released
  with, since newer tauri-runtime, -utils, -macros and wry do not build against it): Alpha's own
  window over the core on 4700 (the token from the data folder), never a core of its own; the
  rail's top space holds the traffic lights and the bars move the window (`data-tauri-drag-region`,
  allowed to the core's pages by a capability); its place kept; links outside Alpha open in their
  own apps, exports land in Downloads; closing hides it. The menu bar mark (the A tile, a dot when
  something waits) with Open Alpha, what needs you, Show/Hide the companion, Activity, Settings,
  Quit. `pnpm mac` builds it (macOS's own xattr first: Python's breaks the bundler).
- **Notifications from Alpha:** the core's `/api/notices` gives the reminders and the cards that
  began waiting since the app last asked, each with its place; the app asks every few seconds and
  shows them through macOS's notification centre (objc2-user-notifications), a click opening the
  place. Cards only when Alpha's window is not in front. While the app asks, the core leaves
  reminders to it; without it, macOS's script runner still shows them.
- **The companion:** the core's `#/companion` page in a see-through, always-on-top window: the
  face (quiet, working, needs you, typing; a blink, the antenna light breathing while it works),
  a bubble (a reminder with Done and Open, a card's two plain choices, else Open in Alpha), a
  working line, and the box (the last of the conversation, the reply as it comes, Send, Open in
  Alpha). The page tells the app its size and where it draws; the window keeps its bottom-right
  corner as it grows, and clicks elsewhere go through. Dragged, it is kept where it was left on
  that display. ⌃⌥A opens the box from anywhere. Face colours are tokens (look.test).
- **The release:** `pnpm release` builds the app and puts the payload inside it, then seals it
  (ad hoc, or the certificate once made); the old launcher is gone. install.sh adds a second login
  item that opens the app quietly (no window), quits the app before an update, and opens the app
  at the end; `alpha open` opens the app; uninstall removes both login items. INSTALL.md says so.
  A trial release from the working tree built the app (684 MB with the payload, 224 MB packed),
  its seal verified, and passed the smoke test. Found on the way: a version given first was
  ignored when no client was named; fixed.
- Tests: 189 (notices; the keep wall, the try). Looked at as the app draws it on Kenil's own Mac:
  the window, the mark, macOS asking about notifications with Alpha's name, the companion in the
  corner sizing itself (88×88, its corner held); the bubbles on made-up stream data in WebKit.
  My request to click in the app was declined, so the drag, the menu and the box await his look.
- **From his look:** a module's pages came up blank (the window refused the `about:srcdoc` frame
  a page draws in: now only web addresses outside Alpha are turned away, and open in their own
  app); the face took two clicks (an unfocused window ate the first: both windows now accept the
  first mouse); and switching modules from a table did nothing, in a browser too (the module
  screen redirected to its *last* module's first table before the new one loaded: the redirect
  now waits for the module's own data). The box and the bubble carry a grip to drag the companion
  by; while the box is open the companion holds every click and scroll. `--at <hash>` opens the
  app at a place, and ALPHA_SHELL_LOG writes what the window lets through, for looking into it.
- **The fresh-Mac run** (evening, Kenil's UTM VM on macOS 26.6.2, made by him; computer control
  for me was refused by the Claude app, so I read the VM's screen with `screencapture` of UTM's
  window): install.sh run from the VM's shared folder failed on thousands of "Too many levels of
  symbolic links" (the share cannot carry pnpm's links) and left a half-copied app; then the
  update path's backup stopped on "ALPHA_HOME is not set". Fixed: install.sh refuses a shared or
  network drive (copy to the Desktop first), clears a half-copied install (no runtime, MANIFEST
  or packages), and exports ALPHA_HOME and ALPHA_LOG_DIR for the core's backup and restore. With
  0.4.1 unpacked on the VM's Desktop the install went through: Alpha in its own window, the
  companion, Avilo's two kits in Settings. He then asked for an install with no Terminal; proposed
  Alpha installing itself on first open (a disk image, an Install window over install.sh, Sign in
  to Claude from Home), with the Open Anyway step until a release is notarized.
- **Alpha installs itself on first open** (his yes, evening; Open Anyway once per Mac until a
  release is notarized, the Apple account later): install.sh takes `--from-app <bundle>` (the app
  as its own source, no sign-in, no opening at the end) and finds its bundle when run from inside
  one (`sh /Volumes/Alpha/Alpha.app/Contents/Resources/app/install.sh`); an app already in
  Applications updates in place; the kits sit inside the app (Contents/Resources/kits); the
  installed version is written to the data folder. A released app (a payload inside) not
  installed, or newer than the one that is, opens one Install window (mac/ui/install.html:
  Install or Update x to y, the installer's lines, Not now) and then opens again from
  Applications; a development build never does. Home's "Sign in to Claude" has a Sign in button:
  the core runs Claude's own sign-in (its browser flow finishes by itself) and the window asks
  every few seconds until the line turns green. The release is a disk image (Alpha.app, an
  Applications link, Read me.md), `alpha update` takes one, INSTALL.md says the new steps.
- **Seen in the VM:** the LinkedIn reader failed every minute on Chrome's "ProcessSingleton"
  call log: the Chrome window Kenil had signed in with was still open and held the site's
  profile. Now the engine says so in words (quit Chrome; Alpha reads it on its next run), and
  when Chrome is not open it clears a stale SingletonLock and reads anyway.
  The same screen showed the reader trying every minute: a failed read never recorded its time,
  so a daily reader that failed was due at every tick. A failed read now waits its own rhythm,
  or half an hour, whichever is shorter, before the next try (kept in the service, so a restart
  tries once). One run of the suite had run.test.ts time out under load; alone it passes.
- **Contacts and Calendar from within Alpha** (his ask from the VM's "contacts access is not

- **The 0.4.4 update, opened from the disk image rather than from Applications:** the
  "installed whole" check looked for `node_modules/@anthropic-ai` at the payload's root, which a
  complete install does not have (pnpm puts it under core/node_modules), so it removed the whole
  0.4.3 app before copying 0.4.4 in; then the core did not answer within 90 s. The check now
  looks only at runtime/node and MANIFEST (the last file a release writes) and sets a partial
  install aside under previous/, never deleting; the download mark is cleared on the copy in
  Applications, where it can be (a disk image is read-only). The core's log from the VM decides
  the rest.
  The VM's core.log settled it: the core started (kits installed, listening) but later than the
  installer's 90 s, since the core installs the kits before it answers and the VM is slow. The
  installer now waits up to ten minutes, says the first start sets up the kits, and reports every
  half minute. 0.4.5 built with that and the whole-install fix.
  Opened afterwards, the app showed its own "Alpha is starting" page: the shell took no answer
  within 2 s for no core. Its health check now waits 8 s (the scripts' curl 10 s), and after half
  a minute the page offers Start Alpha, which starts the core's login item again from the app
  (never "open Terminal"). 0.4.6 built with that.
  A check script in the shared folder (the VM writes its answers back there, so no screenshots
  or copying) showed 0.4.4 installed with its core not running: launchd had the job loaded, no

  Why the first start is slow: main.ts awaits World.open, installInbox (both Avilo kits, each a
